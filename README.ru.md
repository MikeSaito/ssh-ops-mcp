# SSH Ops MCP

Локальный STDIO MCP для работы ИИ с Linux-сервером по SSH: команды, длительные операции, безопасная запись файлов, диагностика и защищённые скачивания. [Подробная документация на английском](README.md).

## Быстрый запуск

Нужны Node.js 22+ и npm. На сервере должны быть Linux, Python 3, SSH и SFTP. Инструменты для служб и журнала требуют systemd.

```sh
npm ci
node bin/ssh-ops-mcp.js --help
```

Создайте приватный файл подключения вне репозитория по [.env.example](.env.example). Укажите настоящий адрес, пользователя, способ входа и проверенный SSH fingerprint. Примеры содержат только заглушки. На Unix задайте секретным файлам права 0600, на Windows ограничьте ACL своим пользователем.

```dotenv
SSH_HOST=203.0.113.10
SSH_PORT=22
SSH_USERNAME=deploy
SSH_AUTH_METHOD=password
SSH_PASSWORD_FILE=/absolute/private/password.txt
SSH_HOST_FINGERPRINT_SHA256=SHA256:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

Получайте fingerprint через доверенную консоль или администратора, а не просто сканированием сети. Он должен соответствовать ключу, выбранному SSH-библиотекой при согласовании алгоритма. Без fingerprint запуск отклоняется; отключение проверки возможно только явно через опасный `SSH_ALLOW_UNVERIFIED_HOST=true`, не для продакшена.

Проверка настроек без подключения и вывода секретов:

```sh
node bin/ssh-ops-mcp.js --env-file /absolute/private/server.env --check-config
```

## Способы входа

| Способ | Поля |
| --- | --- |
| Пароль | `SSH_AUTH_METHOD=password`, `SSH_PASSWORD` либо `SSH_PASSWORD_FILE` |
| Приватный ключ | `SSH_AUTH_METHOD=private_key`, `SSH_PRIVATE_KEY_PATH` |
| Ключ с passphrase | Те же поля + `SSH_KEY_PASSPHRASE` либо `SSH_KEY_PASSPHRASE_FILE` |
| SSH-agent | `SSH_AUTH_METHOD=agent`, `SSH_AGENT_SOCKET` или `SSH_AUTH_SOCK` на Unix; на Windows по умолчанию OpenSSH named pipe |

Любой пользователь и порт задаются явно; `root` не подставляется автоматически. Используйте приватный ключ в формате OpenSSH/PEM, а не `.pub` или `.ppk`. Перебора других способов входа нет, agent forwarding выключен. MFA, SSH config, ProxyJump и сертификаты SSH не заявлены как поддерживаемые. Аппаратный ключ зависит от совместимого агента и отдельно не проверялся.

Относительные пути ключей/секретов считаются от каталога выбранного env-файла; поддерживается `~/`. Значения окружения процесса важнее env-файла: убирайте старые `SSH_*` переменные при смене профиля. Без `--env-file` читается только `.env` внутри этой копии, не соседний приватный проект.

## Подключение к Codex

Готовый пример с двумя серверами: [examples/codex.toml](examples/codex.toml). Замените абсолютные пути; секреты храните в приватных env-файлах, не в TOML.

```toml
[mcp_servers.ssh_prod]
command = "node"
args = ["/absolute/path/ssh-ops-mcp/bin/ssh-ops-mcp.js", "--env-file", "/absolute/private/prod.env"]
startup_timeout_sec = 20
tool_timeout_sec = 120
default_tools_approval_mode = "prompt"
```

На Windows путь может быть `C:/tools/ssh-ops-mcp/bin/ssh-ops-mcp.js`. Для Unix agent добавьте `env_vars = ["SSH_AUTH_SOCK"]`. После изменения настроек переподключите MCP. [Официальная инструкция](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Для клиентов с JSON-настройками есть [пример](examples/mcp-client.json).

Каждый MCP-процесс подключается к одному профилю. Несколько записей с разными именами позволяют одновременно работать с несколькими серверами. Состояние изолировано по адресу, порту и пользователю в `~/.ssh-ops-mcp/state/<target-hash>`; `SSH_MCP_STATE_DIR` меняет базовый каталог, но изоляция сохраняется. Обычный облачный чат не получает доступ к локальному STDIO без поддерживающего его локального клиента/исполнителя.

## Важные правила работы

### Отчёт, этапы и история

У ssh_operation_start появились title и steps: вместо command можно передать до 20 именованных этапов с name и command. Каждый этап выполняется в отдельном bash; cwd и export между ними не сохраняются. Таймаут общий для всех этапов; ошибка/отмена/таймаут пропускают оставшиеся этапы без отката сделанного.

ssh_operation_report(operation_id) объединяет этапы, UTC-время, ожидание запуска, длительности, код выхода и объяснение результата. Команд и содержимого логов в нём нет. Старые операции доступны с legacy_metadata=true и неполными временами; неизвестные значения не подменяются догадками.

ssh_deploy_lock_status показывает название удерживающей задачи, request_id, operation_id, текущий этап, время работы и рекомендацию. При занятом ресурсе новый запуск возвращает resource_busy, outcome=not_started и владельца блокировки. process_lost по-прежнему требует проверки перед снятием блокировки.

Историю можно искать через ssh_operation_list: query по названию/ID/ресурсу, states, точный resource, даты создания created_after / created_before с часовым поясом и limit=1..100. Для следующей страницы передавайте next_cursor как cursor с неизменными фильтрами. Поиск не читает команды и логи. Повреждённые записи учитываются в unavailable_count; история сканирует метаданные, отдельного индекса нет. Названия задач/этапов и request_id должны быть без секретов.

### Выполнение и безопасность

- Для деплоя используйте `ssh_operation_start`, сохраняйте `operation_id` и стабильный `request_id`. После обрыва проверяйте статус/логи; не запускайте ту же миграцию с новым ID. Повтор ID не является транзакцией или гарантией однократных последствий при любой аварии.
- Одинаковый `resource` и SSH-пользователь координируют чаты при деплое одного приложения. `ssh_exec`, внешние команды и другие OS-пользователи могут обойти блокировку.
- Обрыв SSH не останавливает длительную операцию. Отмена/таймаут завершает её группу процессов без отката сделанного; специально отсоединённые процессы могут пережить отмену. У синхронного `ssh_exec` при обрыве результат неизвестен.
- Файлы: сначала hash и preview, затем запись с `expected_sha256`. `null` означает новый файл. Можно проверить временный файл через `validate_command` с `{path}`; существующие владелец/права сохраняются, резервные копии приватные.
- Скачивания: сохраняйте `transfer_id`, проверяйте прогресс, продолжайте тот же ID. Для дампов задавайте `encrypt: true`. Изменённый источник или повреждённые данные не продолжаются автоматически.
- Загрузки на сервер читают `transfers/` внутри пакета; скачивания сохраняются в `transfers/` внутри каталога состояния конкретного подключения. Инструменты возвращают фактический путь.
- Срок хранения скачиваний по умолчанию 7 дней. Очистка работает во время работы MCP и при следующем старте. Явно расшифрованный экспорт автоматически не удаляется. На Unix ключ шифрования хранится приватным файлом, на Windows защищён DPAPI CurrentUser.
- Для проверки `.env` используйте `ssh_secret_presence`, не чтение значений. Маскирование эвристическое и не гарантирует скрытия любого секрета.

При входе не под root сетевые/сервисные проверки выполняются под текущим пользователем. При входе root нужен отдельный аккаунт `mcp-diagnostics`: без sudo, пароля, интерактивной оболочки и привилегированных групп. Его создаёт администратор; отсутствие аккаунта приводит к отказу диагностики, а не выполнению её под root. Альтернативное имя задаётся `SSH_DIAGNOSTIC_USER`.

Все остальные инструменты имеют права выбранного SSH-пользователя. Если это root, ИИ фактически получает полный контроль над сервером. Надписи ADMIN, фильтры и подтверждения клиента не заменяют ограничения Linux. [Модель безопасности и ограничения](SECURITY.md).

## Проверки и публикация

```sh
npm run check
npm test
npm run test:operations
npm run check:release
npm pack --dry-run
```

Тесты используют синтетические секреты и локальные тестовые SSH/agent-серверы, не настоящий сервер. test:operations проверяет операции и блокировки в приватных временных каталогах Linux; на Windows/macOS он пропускается. CI настроен для Windows/macOS/Ubuntu и Node 22/24. [Как выпустить релиз](RELEASING.md).
